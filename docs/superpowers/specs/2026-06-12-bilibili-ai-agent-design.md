# B 站视频资产 AI 分析 Agent 设计方案

## 1. 项目定位

本项目是一个面向个人重度 B 站用户的作品型 MVP，目标不是一开始做成大而全的平台，而是做出一个适合学习、适合求职展示、难度可控的 Java 后端 + AI 应用项目。

项目核心定位为：

> 一个面向 B 站视频资产的 AI 分析 Agent：支持同步个人视频资产、发起异步分析、沉淀知识卡片，并基于知识卡片进行可追溯问答；用户画像和推荐作为轻量增强能力。

第一版优先证明以下三项能力：

1. 能把外部视频资产接入到系统，并做好多用户数据隔离。
2. 能把视频分析做成一个真正可追踪、可重试、可留痕的异步 AI 任务系统。
3. 能把分析结果沉淀为知识卡片，并支持基于知识卡片的可追溯问答。

## 2. MVP 目标与边界

### 2.1 MVP 必做

1. 平台用户注册与登录。
2. 用户绑定 B 站账号会话。
3. 同步用户历史记录、收藏、稍后再看，形成视频资产工作台。
4. 用户对任意视频发起基础分析或深度分析。
5. 异步分析任务系统，具备状态机、失败重试、去重控制、错误留痕。
6. 结构化分析结果输出，包括摘要、核心观点、关键词、争议点、用户态度建议、分析依据。
7. 用户手动将分析结果沉淀为知识卡片。
8. 基于知识卡片、分析结果和来源记录进行可追溯问答。
9. 模型调用失败处理，包括超时控制、失败重试、结构化输出校验、错误落库、降级提示。
10. Prompt 与模型追踪，包括模型名称、Prompt 版本、原始输出、解析结果。
11. 成本控制，包括每日分析次数限制、同视频短时间重复分析限制、分析结果复用、问答频率限制。

### 2.2 MVP 轻量做

1. 轻反馈体系，前端使用网络化标签，后端映射成标准信号。
2. 轻量用户画像，支持画像摘要和简单演化记录。
3. AI 预制问题词条，降低用户提问门槛。
4. 轻量推荐，强调可解释与多样性，不追求复杂算法。

### 2.3 MVP 明确不做

1. 不做浏览器插件正式落地，只预留接口和扩展位。
2. 不做边看边实时同步。
3. 不做多平台内容接入，第一版只做 B 站。
4. 不做传统文档上传型知识库。
5. 不做复杂推荐算法、排序系统、向量召回混排。
6. 不做微服务拆分。
7. 不做消息队列、Elasticsearch、向量数据库等重基础设施。
8. 不做企业租户、组织、复杂角色权限体系。
9. 不做全自动批量深度分析，避免 Token 成本失控。

## 3. 用户与场景

### 3.1 目标用户

目标用户是个人重度 B 站用户，尤其适合：

1. 经常看大量技术、商业、知识类视频的人。
2. 希望把看过的视频沉淀为自己的知识资产的人。
3. 想通过反馈让系统逐步理解自己口味的人。

### 3.2 典型使用场景

1. 用户绑定 B 站账号后，系统自动同步自己的历史记录、收藏和稍后再看。
2. 用户进入视频资产工作台，挑选某个视频发起分析。
3. 系统输出摘要、观点、关键词、争议点、用户态度建议。
4. 用户可对视频做轻反馈或写长评。
5. 用户可选择将视频沉淀为知识卡片。
6. 用户可围绕自己的知识卡片和历史分析结果进行问答。
7. 系统可基于用户画像与反馈信号生成轻量推荐。

## 4. 系统架构

### 4.1 架构形态

第一版采用前后端分离 + 后端模块化单体架构。

推荐原因：

1. 复杂度可控，适合作品型项目。
2. 模块边界清晰，便于后续逐步扩展。
3. 面试时更容易讲清楚业务流、任务流和 AI 流程。

### 4.2 后端模块划分

建议按业务域拆分为以下模块：

1. `auth`：平台注册、登录、鉴权、数据隔离。
2. `bili`：B 站账号绑定、会话管理、数据同步。
3. `video`：视频资产管理、查询、筛选。
4. `analysis`：分析任务创建、调度、执行、结果存储。
5. `feedback`：轻反馈、长评、反馈标签映射。
6. `knowledge`：知识卡片生成、管理、来源追踪。
7. `profile`：用户画像生成与演化记录。
8. `qa`：问答入口、检索、答案生成与溯源。
9. `recommend`：轻量推荐与推荐理由生成。
10. `common`：公共异常、工具类、响应封装、枚举常量。

### 4.3 技术栈职责

1. `Spring Boot`：承载接口、业务流程、任务调度和模块组织。
2. `MySQL`：存储用户、视频、任务、分析结果、知识卡片、画像、问答与推荐记录。
3. `MyBatis-Plus`：承接标准 CRUD 和分页查询。
4. `Redis`：存储缓存、任务运行态、去重键、限流计数和短期行为信号。
5. `Lua`：实现 Redis 原子操作，例如任务去重和限次。
6. `Redisson`：实现分布式锁、限流、任务协调。
7. `LangChain4j`：负责视频分析、知识卡片生成、画像总结、问答与推荐理由生成。

## 5. 数据隔离与权限设计

第一版虽然是轻量多用户系统，但必须明确保证数据隔离。

### 5.1 数据隔离原则

1. 用户只能看到自己的 B 站绑定信息。
2. 用户只能同步和分析自己的视频资产。
3. 用户只能查看自己的分析任务、知识卡片、问答记录、画像和推荐结果。
4. 所有查询必须附带 `user_id` 条件，避免越权访问。

### 5.2 通用字段建议

核心业务表统一带以下字段：

1. `user_id`
2. `created_at`
3. `updated_at`
4. `deleted`

这有助于实现数据隔离、审计信息记录和逻辑删除。

## 6. 核心数据模型

### 6.1 用户与绑定

- `user`
  - 平台用户表。

- `user_bili_account`
  - 用户绑定的 B 站账号信息。
  - 关键字段建议：`user_id`、`bili_uid`、`cookie_snapshot`、`bind_status`、`last_sync_time`

### 6.2 视频本体与用户来源

- `video`
  - 存视频本体数据，避免重复。
  - 关键字段建议：`bvid`、`title`、`author_name`、`cover_url`、`intro`、`publish_time`、`duration`

- `user_video_source`
  - 存用户侧的视频来源。
  - 关键字段建议：`user_id`、`video_id`、`source_type`、`source_time`

说明：

1. 不把 `source_type` 直接放在视频主表。
2. 同一视频对同一用户可同时存在多个来源，例如既在历史记录里，也在收藏里。

### 6.3 分析任务与结果

- `video_analysis_task`
  - 存异步分析任务。
  - 关键字段建议：`user_id`、`video_id`、`analysis_type`、`status`、`retry_count`、`error_message`、`started_at`、`finished_at`

- `video_analysis_result`
  - 存结构化分析结果。
  - 关键字段建议：`task_id`、`summary`、`core_points_json`、`keywords_json`、`controversies_json`、`attitude_suggestion`、`source_basis_json`、`model_name`、`prompt_version`、`raw_response`、`parsed_result`

说明：

1. 结果必须可追踪。
2. 除内容本身外，还要保留模型名称、Prompt 版本、原始输出和解析结果。

### 6.4 反馈信号

- `feedback_label_dict`
  - 前端热梗标签和后端标准信号映射表。
  - 关键字段建议：`label_name`、`signal_type`、`weight`

- `video_feedback`
  - 用户轻反馈与长评记录。
  - 关键字段建议：`user_id`、`video_id`、`feedback_type`、`feedback_label_id`、`content`

说明：

1. 前端可展示“神了”“拉了”“有点东西”“太水了”等灵活标签。
2. 后端统一映射成“喜欢、反感、好奇、无感、值得深挖”等标准信号。

### 6.5 知识卡片

- `knowledge_card`
  - 用户沉淀的知识资产。
  - 关键字段建议：`user_id`、`video_id`、`analysis_task_id`、`analysis_result_id`、`title`、`summary`、`key_points_json`、`tags_json`

说明：

1. 知识卡片必须能追溯到来源视频和来源分析任务。
2. 这是后续可追溯问答的关键基础。

### 6.6 用户画像

- `user_profile`
  - 当前画像主表。
  - 关键字段建议：`user_id`、`profile_summary`、`interest_tags_json`、`dislike_tags_json`、`curiosity_tags_json`

- `user_profile_evolution`
  - 画像演化日志。
  - 关键字段建议：`user_id`、`trigger_type`、`trigger_ref_id`、`change_reason`、`before_snapshot`、`after_snapshot`

说明：

1. 画像不只存当前结论，还要存变化过程。
2. 便于解释“用户兴趣是如何逐步形成的”。

### 6.7 问答与推荐

- `qa_session`
  - 问答记录。
  - 关键字段建议：`user_id`、`question`、`answer`、`source_refs_json`

- `recommendation_record`
  - 推荐记录。
  - 关键字段建议：`user_id`、`video_id`、`profile_snapshot`、`recommend_reason`、`diversity_reason`、`score`

说明：

1. 推荐记录必须保存当时依据，避免画像变化后无法解释历史推荐。

## 7. 分析任务状态机

分析任务必须设计成可追踪的状态机。

### 7.1 建议状态

1. `PENDING`
2. `RUNNING`
3. `SUCCESS`
4. `FAILED`
5. `CANCELED`
6. `RETRYING`

### 7.2 状态流转

1. `PENDING -> RUNNING -> SUCCESS`
2. `PENDING -> RUNNING -> FAILED`
3. `FAILED -> RETRYING -> RUNNING`
4. `PENDING -> CANCELED`

### 7.3 状态机价值

1. 体现异步任务系统能力。
2. 便于错误留痕和失败重试。
3. 便于前端展示任务进度和诊断结果。

## 8. 核心业务流程与 Agent 工作流

### 8.1 视频同步流程

1. 用户登录平台。
2. 用户绑定 B 站会话。
3. 系统拉取历史记录、收藏、稍后再看。
4. 写入 `video` 视频本体。
5. 写入 `user_video_source` 用户来源记录。
6. 更新同步状态和时间。

### 8.2 视频分析流程

1. 用户在视频资产工作台选择某个视频。
2. 选择发起基础分析或深度分析。
3. 系统创建分析任务，状态为 `PENDING`。
4. 后台任务消费者取任务并加锁执行。
5. 收集标题、简介、标签、评论、字幕等可用素材。
6. 通过 LangChain4j 发起结构化分析。
7. 写入分析结果。
8. 更新任务状态为成功或失败。

### 8.3 反馈与画像更新流程

1. 用户查看分析结果。
2. 用户提交轻反馈或长评。
3. 系统将前端标签映射为标准信号。
4. 画像模块综合分析结果、反馈内容、知识卡片沉淀记录。
5. 更新用户画像摘要和标签。
6. 写入画像演化日志。

### 8.4 问答流程

1. 用户点击 AI 预制问题词条，或自由输入问题。
2. 系统检索相关知识卡片。
3. 补充相关视频分析结果、反馈记录、画像快照。
4. 通过 LangChain4j 生成回答。
5. 返回答案及引用依据。

### 8.5 推荐流程

第一版推荐只做轻量实现。

1. 系统读取当前画像和近期反馈。
2. 从候选视频池中筛选内容。
3. 按主兴趣、延伸兴趣、探索兴趣进行简单打分。
4. 生成推荐理由和多样性说明。
5. 写入推荐记录。

## 9. 推荐机制与防同质化策略

第一版推荐强调可解释与多样性控制，不追求复杂算法。

### 9.1 推荐池划分

1. 主兴趣池：优先命中用户稳定偏好。
2. 延伸池：从主兴趣周边做适度扩展。
3. 探索池：根据“特别好奇”等信号加入跨领域内容。

### 9.2 推荐比例建议

1. `70%` 主兴趣池
2. `20%` 延伸池
3. `10%` 探索池

### 9.3 推荐分数思路

推荐分数可以由以下部分组成：

1. 兴趣匹配分
2. 好奇探索分
3. 知识沉淀相关分
4. 负反馈惩罚
5. 近期重复惩罚

### 9.4 防同质化规则

1. 同主题重复推荐惩罚。
2. 每批推荐保底一定比例探索内容。
3. 用户强烈反感内容降权或屏蔽。
4. 近期刚分析过或大量浏览过的同类内容降权。

## 10. 模型调用兜底与可追踪设计

AI 模型属于不稳定外部依赖，不能把模型输出直接视为可信业务数据。

### 10.1 需要覆盖的异常

1. 调用超时
2. 接口限流
3. Token 超限
4. 响应为空
5. 返回结构不合法
6. JSON 解析失败
7. 模型服务不可用

### 10.2 第一版最少落地策略

1. 超时控制
2. 失败重试
3. 错误落库
4. 结构化输出校验
5. 降级提示

### 10.3 可追踪设计

分析结果与问答记录中建议保留：

1. `model_name`
2. `prompt_version`
3. `raw_response`
4. `parsed_result`

这样可以支持后续排查、回溯与 Prompt 迭代。

## 11. 成本控制设计

由于深度分析和问答会消耗较多 Token，第一版必须显式控制成本。

### 11.1 控制策略

1. 每个用户每日深度分析次数限制。
2. 同一视频短时间内禁止重复深度分析。
3. 优先复用已有分析结果。
4. 问答接口做频率限制。
5. 长字幕内容先做摘要，再做深度分析。
6. 只保留必要上下文，不无限拼接历史信息。

### 11.2 技术映射

1. `Redis`：计数、缓存、频控。
2. `Lua`：原子限次与去重。
3. `Redisson`：限流和并发控制。
4. `MySQL`：分析结果复用和历史留痕。

## 12. 页面与用户操作路径

第一版页面不求复杂，但必须能支撑核心闭环。

### 12.1 页面建议

1. 登录页
2. B 站绑定页
3. 视频资产工作台
4. 视频分析详情页
5. 知识卡片页
6. 问答页
7. 画像页
8. 推荐页

### 12.2 用户主路径

1. 用户注册并登录。
2. 绑定 B 站账号。
3. 同步自己的视频资产。
4. 在工作台选择视频发起分析。
5. 查看结构化结果。
6. 选择沉淀为知识卡片。
7. 基于知识卡片问答。
8. 可选提交反馈并查看画像与推荐。

## 13. 简历与答辩主打亮点

建议把项目亮点固定成以下四项：

1. 异步视频分析任务系统：状态可追踪，失败可重试。
2. 可追溯知识问答：回答可关联来源视频、分析结果和知识卡片。
3. 可解释画像演化：用户兴趣由反馈和内容分析持续更新。
4. 轻量多样性推荐：兼顾主兴趣和探索内容，避免完全同质化。

## 14. 后续演进方向

如果第一版完成良好，二期可以考虑：

1. 浏览器插件接入，实现边看边点评。
2. 更多推荐策略和推荐反馈闭环。
3. 更细粒度的画像更新机制。
4. 更多内容来源平台接入。
5. 更正式的部署和运维方案。

## 15. 第一版结论

第一版不追求做成复杂平台，而是聚焦于：

1. 真实视频资产接入。
2. 异步 AI 分析任务。
3. 知识卡片沉淀。
4. 可追溯问答。

这是最适合学习、最适合讲清楚、也最适合作为求职作品的切入点。
